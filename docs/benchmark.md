# 현재 프로젝트 벤치마크

대상은 **현재 프로젝트**로만 표시한다. 식별 정보, 원본 코드, 경로, 파일명, 내부 구조와 상세 로그는 저장소에 포함하지 않는다.

## 2026-11-02 · 현재 프로젝트 전체 빌드

세 모드 모두 빈 출력 폴더에서 최종 x64 실행 파일 링크까지 두 번씩 성공했다.

| 모드 | 1회차 | 2회차 | 평균 |
|---|---:|---:|---:|
| 순정 로컬 | 311.33초 | 283.80초 | 297.57초 |
| DBE Local | 298.46초 | 301.95초 | 300.20초 |
| DBE Hybrid (Worker 두 대) | 670.77초 | 675.96초 | 673.36초 |

프로젝트 Build와 명시된 참조 프로젝트를 VS 2026 MSBuild로 실행했다. Debug x64, 동일 MSVC Hostx64, 원래 PCH·MP 설정, MSBuild 병렬도 4를 사용했다. 일반 앱을 켜 둔 채 1회차는 표 순서로, 2회차는 역순으로 측정했다. 매번 새 출력 폴더를 사용했고 OS 캐시는 유지했다. 기존 생성 입력을 사용하고 생성·설치·배포 이벤트는 공통으로 제외했다.

다른 빌드가 겹쳐 중단한 예비 실행 한 건은 집계에서 제외했다. 유효한 여섯 실행 전후에 검사한 소스와 프로젝트 파일의 목록·해시는 일치했다. 외부 SDK 전체는 해시 검사 범위 밖이다.

DBE Local의 평균 차이는 순정 대비 +2.64초(+0.9%)였고, 두 회차에서 빠른 쪽이 서로 달랐다. Hybrid는 두 Worker가 반환한 object를 매회 링크했으며 평균 소요 시간은 순정의 2.26배였다. 요청 PC 프로세스군의 평균 CPU 시간은 순정 2,098초, DBE Local 2,091초, Hybrid 2,609초였다. Hybrid에서는 compiler PDB와 로컬·원격 슬롯을 기다린 기록이 반복됐다. 각 대기가 완료 시간을 얼마나 늘렸는지, Worker CPU 시간과 실제 전송량은 추가 계측이 필요하다.

## 2026-10-30 · 수정과 재측정

실제 MSVC MP에서 object 출력 경로 240/259자는 성공하고 261/280자는 C1083/D8040으로 실패했다. 261자 경로의 relative/extended-prefix 표기도 실패했다. compiler 출력은 짧은 소유 폴더로 분리하고, 상태 경로를 명시적으로 짧게 지정할 수 있도록 수정했다. 이 결과는 모든 Windows 긴 경로 지원을 뜻하지 않는다.

Local 전용은 native wrapper로 원래 MSVC PCH/MP를 전달한다. 기존 managed Local 경로의 Worker용 제한을 거치지 않는다. 같은 compiler와 옵션을 사용하며 실패한 object 정리는 원래 MSBuild 동작을 유지한다.

| 합성 검증 | 통과 |
|---|---:|
| wrapper 인자·진단·설정 identity·종료 | 10 |
| Local 증분·include 변경·오류 복구·no-op | 11 |
| Hybrid PCH/PDB·MP·긴 파일명·Debug/Release | 9 |
| 실제 MP 자식 취소·예약·staging 정리 | 5 |

현재 프로젝트의 첫 비교는 측정 도중 입력이 변경돼 무효 처리했다. 고정 입력으로 재시작한 측정에서는 외부 빌드 중첩을 확인해 소유한 측정 Job만 중단했다. 고정 입력의 전후 해시는 일치했다. **두 시도 모두 성능 비교나 가속률의 근거로 사용하지 않는다.** 일반 앱은 그대로 유지한다.

이후 순정 솔루션 진입점은 278.583초에 LNK1181로 실패했다. 같은 출력물에 표준 프로젝트 Build를 호출하자 재컴파일 없이 링크까지 성공했다. 따라서 다음 비교는 두 모드 모두 동일한 프로젝트 Build와 명시 참조를 대상으로 한다. 솔루션 전체 빌드와는 범위가 다르며, 이 진단 성공을 fresh-build 시간으로 합산하지 않는다. 원본 프로젝트 파일이나 컴파일 옵션은 수정하지 않았다.

다른 빌드가 다시 실행 중인 것을 확인하여 측정 시작을 차단했다. 사용자 요청에 따라 코드 수정·합성 검증을 먼저 마무리하고 반복 성능 측정은 보류한다. 현재 프로젝트의 수정 후 Hybrid 전체 빌드 검증도 남아 있다.

재측정은 fresh-output 순서를 교대로 바꾸고 warm no-op을 별도로 확인한다. 컴파일러 호출과 object 수정 시각으로 no-op을 검증한다. 시작 전과 실행 중 외부 빌드 중첩을 검사하고, 중첩 시 소유한 측정 Job만 중단한다. CPU 시간과 peak process-family commit도 로컬 증거에 기록하며, 원본 로그와 측정용 프로젝트별 스크립트는 Git에서 제외한다. Agent token 비용은 측정하지 않았다.

## 2026-10-29 · 이전 결과

| 실행 | 일반 로컬 | DBE | DBE 결과 |
|---|---:|---:|---|
| A | 274.247초, 성공 | 1,928.442초 | 링크 입장 대기로 중단 |
| B | 276.404초, 성공 | 264.930초 | 입장 대기 시간 초과로 실패 |
| C | 290.930초, 성공 | 716.662초 | C1083/D8040으로 실패 |

일반 로컬은 4분 34초~4분 51초에 성공했다. 최신 DBE는 11분 57초에 실패했다. **완료한 DBE 전체 빌드 시간이 없으므로 가속률을 계산하지 않는다.** B의 짧은 실패 시간을 성능 향상으로 해석하지 않는다.

## 조건과 한계

- 동일 MSVC Hostx64, 원래 PCH/MP 설정과 동일 빌드 구성. baseline을 DBE에 맞춰 제한하지 않았다.
- 일반 앱을 유지하고 별도 출력 디렉터리를 사용했다. 백그라운드 부하와 OS cache 상태는 완전히 통제하지 않았다.
- 기존 생성 입력을 사용하고 외부 부수 효과가 있는 build event는 측정에서 제외했다. 일상 빌드의 이벤트 범위와 다르다.
- 원격 Worker 두 대를 사용했다. 전체 성공, 실제 프로젝트의 반복 no-op 비교와 Worker CPU/메모리/실제 전송량 계측은 완료하지 못했다.
- 당시 최종 오류의 원인은 미확정이었다. 위 재현으로 경로 길이 실패를 구분했으며, 수정 후 현재 프로젝트의 전체 Hybrid 성공은 추가 확인이 필요하다.

## 후속 검증

전체 빌드 비교를 마쳤다. 무변경·소스 변경·헤더 변경 시의 반복 시간과 Hybrid의 단계별 비용을 [열린 이슈](issues.md)에서 추적한다.
