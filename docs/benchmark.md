# 현재 프로젝트 벤치마크

## 2026-11-03 · 엔진 0.2.3의 실제 전체 검증

요청 측 런타임은 0.2.3, 수신 Worker는 0.2.3과 기존 0.2.2이며 v6로 통신했다. 동일한 MSVC 19.44.35229.0을 사용했다. 현재 프로젝트의 Build와 명시 참조를 대상으로 기존 PCH·MSVC 옵션·소스를 유지했다. 솔루션이 주입하는 순서용 참조 전체를 검증한 것은 아니다. 동일 compiler, Debug x64, `/m:4`, 기존 생성 입력과 compile/link만 사용하며 버전 갱신·배포 등 외부 부수 효과가 있는 이벤트는 두 모드에서 제외했다. 실제 프로그램은 실행하지 않았다. 솔루션과 측정 대상 소스·프로젝트 설정 목록의 전후 membership·hash를 확인했으며 SDK·외부 소스 전체를 불변 snapshot으로 고정한 검증은 아니다.

C:의 분리된 fresh-output을 사용하는 각 1회 관측이다. 순서는 Hybrid 다음 순정이며 OS cache를 초기화하지 않았다. Worker 한 대는 복구한 새 상태, 다른 한 대는 기존 blob cache를 사용했다. 일반 앱과 VS를 열어 두었다. Hybrid 중 `/Zs /analyze`의 IDE 백그라운드 분석을 확인했고 원래 모니터의 중첩 표시는 로컬 증거에 그대로 남겼다. 백그라운드 부하가 변하므로 **통제된 반복 가속률이 아닌 이번 환경의 참고 비교**다.

| 모드 | 전체 Build | 반복 Build | 요청 PC CPU | 최대 프로세스군 commit |
|---|---:|---:|---:|---:|
| 순정 로컬 | 326.54초 | 36.41초 | 2,135.14초 | 22.87GiB |
| 두 Worker Hybrid | 1,014.07초 | 52.57초 | 1,531.47초 | 22.17GiB |

전체 시간의 관측 비율은 약 3.11배다. 요청 PC CPU 감소를 전체 가속으로 해석하지 않는다. 실패·중단된 실행은 위 시간에서 제외했다. 순정의 앞선 실행은 별도 MSBuild 감지로 약 280.65초에 소유한 Job만 중단했으며 완료 시간으로 사용하지 않는다.

Hybrid는 로컬 656개, 원격 426개(두 Worker에서 각각 209개·217개)를 완료했다. fallback 0개이며 최종 객체·PDB 링크가 성공하고 링크 경고가 없었다. 원본 입력 전후 해시는 일치했다. 반복 Hybrid는 compiler·전처리·RPC 없이 객체 수정 시각을 유지했지만 최종 링크가 한 번 실행됐다. 순정 반복 Build에서도 linker 실행을 확인했다. DBE만의 현상으로 단정하지 않으며 반복 Build를 전체 작업이 없는 no-op으로 주장하지 않는다.

### D:의 별도 Native/Local 참조 쌍

C:의 보존된 증거와 출력이 공간을 차지해 추가 Local 출력은 차단하고, Native/Local을 모두 여유 있는 D:에서 비교했다. C:와 D:의 수치를 하나의 통제된 세 모드 표로 합치지 않는다. 원래 소스·MSVC·PCH/MP·진입점은 같고 각 1회다.

0.2.3의 D: 순정 전체 334.83초, DBE Local 전체 338.92초로 약 +1.2%였다. 순정 반복 Build는 1.91초였다. Local 반복 Build는 참조 헤더의 입력 범위를 뒤늦게 발견해 compiler를 시작했으므로 약 5초에 소유한 검증만 중단했다. 이 실패 시간을 정상 no-op 시간으로 사용하지 않는다.

0.2.4는 평가된 ProjectReference의 폴더를 첫 검사에 포함하도록 수정했다. 임의로 알려지지 않은 입력을 up-to-date로 판정하거나 컴파일 후의 새 fingerprint를 덮어써 원인을 숨기지 않는다. 실제 참조 헤더와 그 형제의 없는 include 추가/삭제, 최초 no-op·오류 복구를 포함한 MSBuild 검증 15개를 통과했다. 수정 후 같은 입력을 사용하는 실제 Local 전체 빌드는 354.69초, 최초 반복 Build는 6.10초에 성공했다. 반복 Build의 compiler·linker·librarian 호출과 RPC는 0개였고 객체 수정 시각과 입력 목록·hash가 유지됐다.

| D: 참조 실행 | 전체 Build | 반복 Build | 요청 PC CPU | 최대 프로세스군 commit |
|---|---:|---:|---:|---:|
| 순정 로컬 | 334.83초 | 1.91초 | 2,121.84초 | 22.97GiB |
| 수정 후 DBE Local 0.2.4 | 354.69초 | 6.10초 | 2,150.00초 | 23.03GiB |

수정 후 Local 전체 시간은 이번 관측에서 약 +5.9%였다. 입력 검사 비용과 변하는 앱 부하가 포함된 단일 회차이므로 원인을 한 항목에 귀속하거나 처리량 동등성이 입증됐다고 주장하지 않는다. 앞선 0.2.3 Local 측정, 합성 검증 후 0.2.4 Local 순서였고 OS cache를 초기화하지 않았다. C: 반복 실행에서 나타난 추가 링크는 D: 순정·수정 Local에서는 재현되지 않았다. 경로·추적·진입점 조건을 분리해 조사해야 하며 모든 추가 링크를 DBE에 귀속하지 않는다.

### 재사용과 실제 전송 비용

완료된 원격 응답 426개에서 입력 트리 hit 414개, PCH hit 398개, compact context 참조 405개를 확인했다. 재사용 자체는 동작하지만 전체 속도 개선을 뜻하지 않는다.

| 기록된 데이터 | 합계 |
|---|---:|
| 요청 header | 232.33MiB |
| 입력 payload | 556.80MiB |
| 소비자 PDB | 14,744.82MiB |
| 기준 PDB 실제 수신 | 274.41MiB |
| 소비자 object | 668.13MiB |

이는 애플리케이션의 완료 응답 영수증 기준이며 TLS/IP overhead, 재시도·실패 트래픽 전체를 캡처한 NIC 계측은 아니다. 소비자마다 독립 PDB를 반환해 기준 PDB 재전송을 줄인 뒤에도 약 14.4GiB의 소비자 PDB가 남는다.

### 요청 PC에서 관측한 단계

| 구간 | task 시간 합 | 중첩을 합친 시간 |
|---|---:|---:|
| 로컬 compiler 실행 | 560.35초 | 544.96초 |
| 원본 입력 snapshot | 451.24초 | 138.81초 |
| 입력 업로드 | 89.72초 | 89.72초 |
| 원격 결과 대기 | 1,405.72초 | 495.81초 |
| 결과 수신·게시 | 309.55초 | 189.22초 |
| 로컬 PDB와 원격 용량 동시 대기 | 407.65초 | 402.69초 |
| Worker 실행 용량 대기 | 1,399.58초 | 380.53초 |

구간들은 서로 겹치며 대기는 이유가 바뀔 때 기록한 관측값이다. 합산해 전체 시간이나 단일 원인 기여율을 계산하지 않는다. 결과 수신·게시 전체를 PDB 전송 시간이라고 부르지 않는다. Worker 영수증의 실행 구간 합은 입력 트리 준비 178.26초, PCH 생성 81.29초, 소비자 실행 744.60초였으며 병렬 경과 시간 합이지 Worker CPU 시간이 아니다. 실제 원격 CPU·physical RAM peak와 agent token 비용은 미측정이다.

### 다음 개선 범위

소비자마다 PDB를 복제·반환하는 소유 단위를 같은 Worker의 여러 컴파일 배치로 묶고, 요청 PC의 원래 병렬 처리량을 보존하는 방향을 먼저 검토한다. 전송만 압축해도 최종 링크가 다수 PDB를 읽는 비용은 남으므로 전송 최적화만으로 해결했다고 보지 않는다. 현재 Hybrid의 로컬 배치는 `/MP2`와 하나의 PDB 소유자로 입장하므로 순정의 원래 fan-out과 다르다. 수신 Worker의 사용자 보호 예산을 높여 수치를 만드는 방식은 사용하지 않는다. 입력 snapshot·최초 트리 구성과 반복 링크도 별도 추적한다. 이 개선은 아직 구현·효과 검증 전이다.


## 2026-11-03 · 큰 PCH와 최초 입력 준비

재개한 전체 검증에서 주요 PCH 두 개가 약 989MiB·1,111MiB임을 확인했다. 0.2.0의 512MiB 디스크 한도로 원격 처리가 거절되고 같은 PCH 생성이 반복돼, 소유한 실행만 중단했다. 원본 소스의 전후 해시는 일치했다. **이 실행도 전체 성공 시간으로 사용하지 않는다.**

0.2.1 수정 경로를 현재 프로젝트의 실제 입력으로 별도 검증했다. 원래 PCH 설정·옵션으로 Worker가 PCH를 만들고 같은 입력·PCH를 반복 컴파일에서 재사용했다. 각 MSVC의 120초·2GiB 제한을 유지했다.

| 사례 | 원래 PCH 규모 | 첫 요청 | 재사용 요청 |
|---|---:|---:|---:|
| A | 약 989MiB | 230.62초 | 1.01초 |
| B | 약 1,111MiB | 101.15초 | 2.95초 |

A는 빈 blob/context 캐시에서 시작했고 B는 blob 캐시를 공유하되 새 컨텍스트를 구성했다. OS cache는 초기화하지 않았다. 입력 준비·PCH 생성 비용이 다른 요청이므로 가속률이나 순정 로컬 대비 성능으로 해석하지 않는다. 기존 RPC 전체 180초는 입력 준비 중 만료되는 것을 재현했다. 수정 후 RPC 예산은 compiler 제한 120초 기준 420초이며 각 compiler 제한은 유지한다.

이 루프백 검증 프로세스군 전체는 종료·캐시 정리를 포함해 389.71초, CPU 시간 324.56초, peak commit 약 1.73GiB였다. 물리 RAM peak·agent token 비용과 두 물리 Worker의 동시 대형 PCH 자원 사용은 측정하지 않았다. 수정 후 실제 전체 링크·무변경·동일 조건 순정 비교가 남아 있다.

## 2026-11-03 · v6 입력/PCH 재사용 검증

프로젝트의 PCH 설정과 compiler 옵션을 유지하는 선택 경로에 Worker 입력 트리·PCH 재사용을 구현했다. 두 물리 Worker에서 각각 30개 합성 검증을 통과했고, 요청 PC의 동일 MSVC로 반환 객체를 원래 로컬 producer와 링크·실행했다. DIA로 최종 PDB의 서로 다른 사용자 타입·멤버 정보도 확인했다. 후속 요청에서는 입력 바이트와 기준 PDB를 재전송하지 않았고, 큰 파일 목록 대신 작은 컨텍스트 참조를 보냈다. 소비자 객체와 소비자 PDB는 계속 반환한다.

별도의 로컬 TLS 합성 실험에서 같은 입력·옵션과 warm blob 캐시를 사용한 단일 TU 왕복을 비교했다. v5는 매 요청 입력 트리와 PCH를 구성하고, v6는 이미 준비된 입력 트리와 PCH를 재사용한다. 최초 입력 전송·PCH 생성 시간은 이 표에 포함하지 않는다.

| 회차 | v5 재구성 | v6 재사용 |
|---|---:|---:|
| 1 | 1.445초 | 0.521초 |
| 2 | 1.309초 | 0.707초 |
| 3 | 1.479초 | 0.511초 |

작은 합성 입력의 예비 관측이며 현재 프로젝트의 가속률이 아니다. 각 쌍은 v5→v6 순서로 실행했으므로 순서 효과를 통제한 반복 벤치마크로 해석하지 않는다. 일반 앱은 유지했고 OS cache를 초기화하지 않았다. 이 실험의 프로세스군 CPU 시간·peak 메모리·agent token 비용은 측정하지 않았다.

현재 프로젝트의 두 Worker Hybrid 전체 검증은 다른 빌드 시작을 감지해 360.08초에 소유한 측정만 중단했다. 그때까지 로컬 40개·원격 19개 완료와 입력/PCH cache hit를 확인했고 원본 소스·프로젝트의 전후 해시는 일치했다. **최종 링크가 끝나지 않았으므로 전체 성공 시간이나 속도 비교로 사용하지 않는다.** v6 전체 성공·무변경·순정 대비 재측정은 다른 빌드와 겹치지 않는 시간에 남아 있다.

## 전처리 경로 계측

현재 프로젝트의 기존 전처리본 전송 경로를 계측한 단일 회차에서 Hybrid는 660.06초였다. 로컬 입장 제어와 원격 슬롯의 대기를 분리하고 헤더 검증 결과를 공유한 뒤 동일 조건의 단일 회차는 632.25초였다. 같은 후속 회차의 순정 로컬은 275.50초, DBE Local은 296.60초였다. 이 결과만으로 반복 성능 개선을 확정할 수 없다.

최초 계측에서 전처리 MSVC 실행 구간의 합집합은 189.73초, 전처리본 검증·정규화는 341.70초, 원격 요청에서 결과 반환까지는 542.23초였다. 구간은 서로 겹치므로 합산해서 전체 시간으로 해석할 수 없다. 후속 회차의 원격 결과 대기는 작업별 합계 1843.05초였다. 이 값에는 Worker 실행과 전송 대기가 포함된다. Worker CPU 실행 시간으로 분해한 값은 아직 없다.

공유 PDB를 사용하는 로컬 MP 그룹에서도 긴 단일 컴파일 때문에 다른 MP 작업이 먼저 끝난 뒤 PDB 소유권이 유지되는 사례를 확인했다. batch 크기와 작업 순서 조정은 합성 회귀 검증 대상이며 현재 프로젝트 반복 측정이 남아 있다.

원본 입력과 원격 PCH를 사용하는 v4의 검증 범위는 [별도 문서](native-pch.md)에 기록한다. 위 시간은 기존 전처리본 전송 경로의 측정이다.

대상은 **현재 프로젝트**로만 표시한다. 식별 정보, 원본 코드, 경로, 파일명, 내부 구조와 상세 로그는 저장소에 포함하지 않는다.

## 2026-11-02 · 현재 프로젝트 전체 빌드

세 모드 모두 빈 출력 폴더에서 최종 x64 실행 파일 링크까지 두 번씩 성공했다.

| 모드 | 1회차 | 2회차 | 평균 |
|---|---:|---:|---:|
| 순정 로컬 | 311.33초 | 283.80초 | 297.57초 |
| DBE Local | 298.46초 | 301.95초 | 300.20초 |
| DBE Hybrid (Worker 두 대) | 670.77초 | 675.96초 | 673.36초 |

프로젝트 Build와 명시된 참조 프로젝트를 VS 2026 MSBuild로 실행했다. Debug x64, 동일 MSVC Hostx64, 원래 PCH·MP 설정, MSBuild 병렬도 4를 사용했다. 일반 앱을 켜 둔 채 1회차는 표 순서로, 2회차는 역순으로 측정했다. 매번 새 출력 폴더를 사용했고 OS 캐시는 유지했다. 기존 생성 입력을 사용하고 생성·설치·배포 이벤트는 공통으로 제외했다.

다른 빌드가 겹쳐 중단한 예비 실행 한 건은 집계에서 제외했다. 유효한 여섯 실행 전후에 검사한 소스와 프로젝트 파일의 목록·해시는 일치했다. 외부 SDK 전체는 해시 검사 범위 밖이다.

DBE Local의 평균 차이는 순정 대비 +2.64초(+0.9%)였고, 두 회차에서 빠른 쪽이 서로 달랐다. Hybrid는 두 Worker가 반환한 object를 매회 링크했으며 평균 소요 시간은 순정의 2.26배였다. 요청 PC 프로세스군의 평균 CPU 시간은 순정 2,098초, DBE Local 2,091초, Hybrid 2,609초였다. Hybrid에서는 compiler PDB와 로컬·원격 슬롯을 기다린 기록이 반복됐다. 각 대기가 완료 시간을 얼마나 늘렸는지, Worker CPU 시간과 실제 전송량은 추가 계측이 필요하다.

## 2026-10-30 · 수정과 재측정

실제 MSVC MP에서 object 출력 경로 240/259자는 성공하고 261/280자는 C1083/D8040으로 실패했다. 261자 경로의 relative/extended-prefix 표기도 실패했다. compiler 출력은 짧은 소유 폴더로 분리하고, 상태 경로를 명시적으로 짧게 지정할 수 있도록 수정했다. 이 결과는 모든 Windows 긴 경로 지원을 뜻하지 않는다.

Local 전용은 native wrapper로 원래 MSVC PCH/MP를 전달한다. 기존 managed Local 경로의 Worker용 제한을 거치지 않는다. 같은 compiler와 옵션을 사용하며 실패한 object 정리는 원래 MSBuild 동작을 유지한다.

| 합성 검증 | 통과 |
|---|---:|
| wrapper 인자·진단·설정 identity·종료 | 10 |
| Local 증분·include 변경·오류 복구·no-op | 11 |
| Hybrid PCH/PDB·MP·긴 파일명·Debug/Release | 9 |
| 실제 MP 자식 취소·예약·staging 정리 | 5 |

현재 프로젝트의 첫 비교는 측정 도중 입력이 변경돼 무효 처리했다. 고정 입력으로 재시작한 측정에서는 외부 빌드 중첩을 확인해 소유한 측정 Job만 중단했다. 고정 입력의 전후 해시는 일치했다. **두 시도 모두 성능 비교나 가속률의 근거로 사용하지 않는다.** 일반 앱은 그대로 유지한다.

이후 순정 솔루션 진입점은 278.583초에 LNK1181로 실패했다. 같은 출력물에 표준 프로젝트 Build를 호출하자 재컴파일 없이 링크까지 성공했다. 따라서 다음 비교는 두 모드 모두 동일한 프로젝트 Build와 명시 참조를 대상으로 한다. 솔루션 전체 빌드와는 범위가 다르며, 이 진단 성공을 fresh-build 시간으로 합산하지 않는다. 원본 프로젝트 파일이나 컴파일 옵션은 수정하지 않았다.

다른 빌드가 다시 실행 중인 것을 확인하여 측정 시작을 차단했다. 사용자 요청에 따라 코드 수정·합성 검증을 먼저 마무리하고 반복 성능 측정은 보류한다. 현재 프로젝트의 수정 후 Hybrid 전체 빌드 검증도 남아 있다.

재측정은 fresh-output 순서를 교대로 바꾸고 warm no-op을 별도로 확인한다. 컴파일러 호출과 object 수정 시각으로 no-op을 검증한다. 시작 전과 실행 중 외부 빌드 중첩을 검사하고, 중첩 시 소유한 측정 Job만 중단한다. CPU 시간과 peak process-family commit도 로컬 증거에 기록하며, 원본 로그와 측정용 프로젝트별 스크립트는 Git에서 제외한다. Agent token 비용은 측정하지 않았다.

## 조건과 한계

- 동일 MSVC Hostx64, 원래 PCH/MP 설정과 동일 빌드 구성. baseline을 DBE에 맞춰 제한하지 않았다.
- 일반 앱을 유지하고 별도 출력 디렉터리를 사용했다. 백그라운드 부하와 OS cache 상태는 완전히 통제하지 않았다.
- 기존 생성 입력을 사용하고 외부 부수 효과가 있는 build event는 측정에서 제외했다. 일상 빌드의 이벤트 범위와 다르다.
- 원격 Worker 두 대를 사용했다. 전체 성공, 실제 프로젝트의 반복 no-op 비교와 Worker CPU/메모리/실제 전송량 계측은 완료하지 못했다.
- 당시 최종 오류의 원인은 미확정이었다. 위 재현으로 경로 길이 실패를 구분했으며, 수정 후 현재 프로젝트의 전체 Hybrid 성공은 추가 확인이 필요하다.

## 2026-11-03 · v6 전체 검증 중 발견한 실패

현재 프로젝트의 수정 전 실행은 약 540.57초에 로컬 fallback의 C1060으로 실패했다. 원격 완료 36개를 확인했지만 최종 링크·무변경에 도달하지 못했다. 입력 전후 해시는 일치했다. 다른 빌드를 기록하며 진행한 정확성 검증이므로 성능 비교로 사용하지 않는다.

0.2.3에서 로컬 입장 예약량과 실제 compiler 힙 한도를 분리했다. 실패했던 단일 파일을 원래 PCH·옵션으로 재실행해 성공했다. 실행 98.239초, 요청 PC 프로세스군 CPU 116.125초, 최대 commit 5,051,277,312바이트였다. 단일 호출의 진단 값이며 전체 시간·물리 메모리 사용량·원격 CPU 비용을 뜻하지 않는다. Agent token 비용은 측정하지 않았다. 두 물리 Worker의 전체 링크·무변경·동일 조건 반복 비교는 남아 있다.


## 0.3.0 튜닝 검증 상태

기존 Hybrid의 작은 로컬 MP 그룹과 소비자별 PDB 반환 비용을 줄이기 위해 자체 native Job admission 및 최대 4파일 공유 PDB 배치를 추가했다. 합성 MSVC/TLS·MSBuild·DIA 검증은 통과했으나, 현재 프로젝트 전체·동일 조건 속도 비교와 새 런타임의 두 물리 Worker 검증은 아직 남아 있다. 작은 fixture의 성공이나 PDB 파일 개수 감소를 전체 빌드 가속률로 환산하지 않는다.

첫 로컬 admission 예비 측정은 다른 CMake/MSBuild 빌드와 겹쳐 소유한 측정 Job만 중단했다. 입력 해시는 보존했으며 실패한 실행을 성공 시간이나 속도 개선 근거로 포함하지 않는다. 재측정은 동일 볼륨·입력·진입점·앱 유지 조건으로 Native/Local/Hybrid 전체 및 무변경을 분리하고, 실제 원격 완료·PDB bytes·RPC 수·대기/실행 구간·CPU·peak commit을 함께 확인해야 한다. 요청 PC Job 측정만으로 원격 CPU/메모리 비용을 설명할 수 없다.
